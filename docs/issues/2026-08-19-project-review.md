### ISSUE-002：一次支付凭证可以无限次调用生图

- 优先级：`P0`
- 状态：`已解决`
- 发现时间：`2026-08-19 22:33:13 +08:00`
- 开始处理时间：`2026-08-19 23:13:58 +08:00`
- 解决时间：`2026-08-19 23:30:02 +08:00`
- 解决情况：前端首次生图时创建固定 `generationId` 并写入会话，后续请求沿用该 ID。服务端完成图片与风格校验后计算 SHA-256 请求指纹，再将已支付订单原子绑定到唯一生图任务；不同任务 ID 和相同 ID 但内容不一致的请求均返回 `409`。相同任务的并发请求共享进程内 Promise，成功结果在内存中保留 10 分钟用于安全重放；订单文件只持久化消费状态、请求哈希和任务状态，不写入图片内容。支付凭证增加 24 小时有效期，旧订单按 `paidAt` 兼容计算。
- 相关提交或 PR：暂无，修改尚未提交。
- 代码证据：`server/payment/orderStore.ts:83-89`、`server/routes/generation.ts:92-97`
- 影响：一次成功支付可以被重复请求，无限消耗真实模型供应商额度和费用。
- 建议方向：在服务端建立生图权益消费状态，原子预占和消费权益，增加凭证过期和撤销机制，并使用生图幂等键，让重复请求返回同一个任务而不是再次调用模型。
- 验证证据：`npm run lint` 通过；`npm test` 的 4 个测试文件、12 个测试全部通过；`npm run build` 通过；编译后的服务端使用 mock provider 启动成功，`GET /api/health` 返回 `ok: true`。新增测试覆盖单订单只能绑定一个任务、请求指纹不一致拒绝、消费状态重启后保留、订单文件不保存图片、重复支付回调不重置权益、非法风格不消费权益、成功请求重放和不同任务 ID 返回 `409`。
- 方案边界：当前本地 JSON Store 只能保证单 Node 进程内的同步原子占用；多实例强一致性仍依赖 `ISSUE-004` 中的数据库和唯一索引。成功图片仅在当前进程内短时缓存，服务重启后的作品恢复仍依赖 `ISSUE-004` 和 `ISSUE-005` 的服务端资产存储；当前行为会保留已消费状态并拒绝再次调用模型，避免重复费用。

### ISSUE-003：缺少全局限流和模型供应商并发控制

- 优先级：`P0`
- 状态：`处理中`

- 开始处理时间：`2026-08-20 10:39:01 +08:00`
- 解决情况：日志确认即梦在单批并发 2 个风格时返回 `429` 和 `Request Has Reached API Concurrent Limit`。已暂时将单个生图请求的风格并发数从 2 调整为 1，使最多 4 个风格按顺序生成。该修改只缓解即梦账号并发限制，尚未实现跨请求全局并发控制、队列、限流和退避重试，因此本问题仍为处理中。
